# changelog-curator：Changelog 生成

## 职责

把一段 git 历史整理成一份面向读者的变更说明（changelog）。本技能的核心原则是**策展而非搬运**：原始提交是素材，curator 的工作是分类、合并、改写，让读者一眼看到「这个版本对我意味着什么」，而不是读一遍提交列表。

## 何时使用

- 发版前：确定版本号之后，为 `[新版本]` 生成条目；
- 补历史：仓库从未维护 changelog，从最早提交到当前版本生成一份；
- 维护现有 CHANGELOG.md：新增条目、修正过时的旧条目。

## 输入收集

| 证据 | 获取方式 | 用途 |
|---|---|---|
| 版本范围 | `git tag` 确定上个标签；`git log <prev_tag>..HEAD` | 界定条目区间 |
| 提交列表 | `git log --pretty=format:"%h %s" <prev>..<head>` | 分类素材 |
| 详细变更 | `git log -p <prev>..<head>`（按需，只看关键提交） | 理解提交意图 |
| 合并历史 | 仓库若以 merge/squash 为主，以合并后的提交标题为准 | 避免逐 commit 碎片化 |
| 现有 CHANGELOG | CHANGELOG.md 的既有结构与格式 | 保持风格一致 |

## 工作流程

1. **界定范围**：确认起始点。没有标签就用第一个提交；范围拿不准时问用户。
2. **通读并分类**：把每个提交归入类别：新增（feat）/ 修复（fix）/ 优化（improve）/ 性能（perf）/ 移除（remove）/ 破坏性变更（breaking）。无法归类的内部改动（改测试、格式化、依赖锁定）默认丢弃——除非它影响使用者。
3. **合并同类项**：同一主题的多条提交合并为一条有意义的条目（如「新增登录」的 5 个提交合并为一条）。
4. **改写为读者视角**：把提交标题从「实现者视角」改写为「使用者视角」：说明用户能获得什么，而不是内部动作。
5. **标注破坏性变更**：任何行为/接口变化单独成组，并在条目中显著标注（模板中位于各分类之后）。
6. **按版本输出**：未发版内容归入 `[Unreleased]`；有版本号时生成对应节与日期、对比链接。

## 输出模板与变量

```markdown
# 更新日志

本文件记录本项目的显著变更，格式遵循【类别：新增 / 修复 / 优化 / 性能 / 移除 / 破坏性变更】。

## [Unreleased]

### 新增
{added}
### 修复
{fixed}
### 优化
{improved}
### 性能
{perf}
### 移除
{removed}
### 破坏性变更
{breaking}

## [{version}] - {date}

（分类同上：新增 / 修复 / 优化 / 性能 / 移除 / 破坏性变更）
```

| 模板变量 | 含义 | 示例 |
|---|---|---|
| {version} | 版本号（来自标签或用户指定） | 1.2.0 |
| {date} | 发版日期，格式 YYYY-MM-DD；Unreleased 节不写日期 | 2026-08-16 |
| {added} | 新增功能条目，每条以动词开头、说清用户得到什么 | - 新增从 git 历史生成 changelog 的技能 |
| {fixed} | 修复条目：什么问题在什么场景下被修复 | - 修复 Windows 下路径含空格时安装失败 |
| {improved} | 体验/内部优化（无行为变化或体验向好的变化） | - 校验脚本对错误信息补充行号 |
| {perf} | 性能提升条目，有依据时附数量级 | - 大型仓库扫描提速约 30% |
| {removed} | 移除的功能/接口，注明替代方案 | - 移除 --legacy 参数，请改用 --compat |
| {breaking} | 破坏性变更：影响升级用户的每一条 | - 配置键 rename：custom_dirs → customSkillDirs |

## 风格选项

默认语言跟随用户提问语言，篇幅为「仅使用者可见」。用户可用自然语言覆盖：

- 语言：`语言=简体中文`、`language=en`
- 范围：`范围=全部提交`（包含内部改动，适合维护者自用）、`范围=使用者可见`（默认）
- 篇幅：`篇幅=简洁`（只保留新增/修复/破坏性变更三类）、`篇幅=完整`（默认六类）
- 粒度：`粒度=粗`（按功能域合并）、`粒度=细`（保留每条独立改动）

## 质量检查清单

输出前逐项自检：

- [ ] 每一条都能在指定范围的提交历史中找到对应提交（未被虚构）
- [ ] 类别归属正确，破坏性变更绝不混入其他类别
- [ ] 合并后的条目以使用者视角表述，不含内部动作黑话
- [ ] 版本号、日期、起始标签与用户提供/仓库信息一致
- [ ] 没有重复条目（同一改动多次出现）
- [ ] 与现有 CHANGELOG 的格式风格一致
- [ ] 范围外的提交没有被混入（如上次发版后已记录过的改动）

## 不要做

- 不要把提交标题逐条复制——那是 git log，不是 changelog
- 不要虚构「修复了 X」：修复类条目必须能在提交中找到对应修复
- 不要写「优化了代码结构」这类无法验证的空条目
- 不要忽略破坏性变更，即使它藏在某条提交里
- 不要改动版本号本身：版本决策属于用户，curator 只负责呈现

## 边界情况

- **仓库从未打标签**：从第一个提交开始生成，范围告知用户「覆盖全部历史」。
- **范围内没有提交**：输出空分类说明（如「本版本无新增」），不要编造。
- **提交信息质量差**：以 diff 为补充证据判断意图；无法判断的条目直接丢弃并说明。
- **Monorepo 多包**：先确认 changelog 是按包还是按仓库维护，按对应粒度分组。
- **已有 changelog 且结构不同**：跟随既有文件的结构（本模板仅作默认），把新条目追加到 Unreleased 节。
